Fix these first

Two of these are single-word changes. Together they are why no trainee has accrued skill evidence and why no unsafe-skill alert has ever been sent.

The skills pipeline rejects 100% of submissions

validateSkillEventV20_1_ reads a property that no code ever assigns:

// Code.gs:5687
if (String(catalogEntry.approval || '').toUpperCase() !== 'APPROVED') {
  problems.push('catalog row is not APPROVED');
}

catalogObjectsV19_ — the only builder of that object — maps the APPROVAL STATUS column to status, not approval. I grepped all 10,289 lines: approval: is never assigned. So the check is true for every skill event ever submitted.

The consequence that matters most is not the blocked evidence. It is this, at Code.gs:5983:

var unsafe = prospective.filter(function (ev) {
  return ev.validation === EV_ACCEPTED_V19 && ev.outcome === 'Unsuccessful / unsafe';
});

Nothing is ever ACCEPTED, so unsafe.length is always zero. An FTO who documents that a trainee was unsuccessful or unsafe on a live patient generates no urgent email to anyone. The only mail sent is a generic rejection notice whose body never contains the word "unsafe."

The flag system can be silenced by the person it audits

simplifyFlagsV20_1 does three things in sequence: it writes a review-log row for every burning flag with no human reading any of them, then rewrites each detection formula to consult the log it just wrote, then hides the tab.

// Code.gs:10227
au.getRange(rowN, 2 + c2).setFormula('=IF(' + ackTest + ',"ACK",' + inner + ')');

It is a closed loop: the function fabricates the acknowledgement, then rewires the detector to accept its own fabrication. The key is (trainee, flag-type), not per-event, so once logged, every future flag of that type for that trainee reads ACK permanently. The completion message states "A flag returns on its own only if NEW data re-triggers it." That is false.

The file itself declares this prohibited. redoAuditTabV20_1 writes "Nothing here is dismissed by hand" onto every flag header, and onSheetEdit hard-blocks the bulk-clear checkbox with AUDIT CLEAR-ALL BLOCKED. The code specifies the control, builds the enforcement, then ships a function that defeats it wholesale.

Blocker
Code.gs:10090Code.gs:10094

fixAllFlagsNowV20_1 alters primary records

It flips an FTO's submitted "Scored 1 or 5" answer from No to Yes on the tab of record, then writes narrative text into the evaluation attributed to that FTO — asserting the words are theirs. The FTO never wrote, saw, or approved that sentence.

The practical consequence is worse than the individual rows: the Google Form response history still holds the original answers, so tab 02 and the Forms record now disagree. That divergence is independently discoverable, and once found it puts every evaluation in the workbook in question — including the honest ones.

Corruption
Code.gs:6913Code.gs:8257Code.gs:8654Code.gs:3092

Bulk approval writes decisions onto the wrong rows

The three approval loops capture row numbers in a snapshot before iterating. Each call to recordDecisionForRowV20_1_ sets the status to RECORDED, then triggers a rebuild that reaches sortQueueByTraineeV20_ — which sorts by RECORD STATUS, moving the just-recorded row below the OPEN block and shifting every remaining row up.

The guard at 3089 was added specifically to prevent this, but it only trips on OPEN rows that already hold a decision. These three functions select rows with no decision and fill it one row at a time, so the guard is false on every pass.

From iteration two onward the loop writes the decision, decider, date and canned rationale onto whatever row now occupies that index. One trainee is silently skipped; another is signed off without ever appearing in the confirmation dialog. Later iterations overwrite already-recorded rows, leaving visible cells that no longer match the immutable sign-off record behind them.

recordPendingDecisionsV20_1 is accidentally safe — its candidates all carry decisions, which keeps the sort suppressed. That asymmetry is why this has stayed hidden.

Corruption
Code.gs:8760Code.gs:3069

The phantom repair destroys the decisions it is meant to restore

fixPhantomsNowV20_1 reopens every phantom row to OPEN, then records them one at a time. After the first record, the rebuild chain reaches an unconditional sweep:

// Code.gs:3069
Object.keys(open).forEach(function (key) {
  if (!readyKeys[key]) queue.getRange(open[key], 12).setValue('CANCELLED : CRITERIA CHANGED');
});

A phantom's skill is by definition already decided, so its readiness is SIGNED OFF — not in readyKeys. Every remaining reopened row is cancelled, and the recorder then skips them as "not OPEN."

Only the first phantom is repaired. The rest lose their original status permanently — and the summary reports "Phantoms remaining: 0", because phantomRowsV20_1_ only inspects rows in the three decided states. The cancelled rows are invisible to it. It reports success while having lost the records.

Code.gs:6916Code.gs:8311Code.gs:6322

No evidence gate exists in the write path

recordDecisionForRowV20_1_ — the single writer to the permanent sign-off log — validates form completeness and decider authority. It never consults skillReadinessV19_, the evidence log, or any threshold. The readiness column is advisory only.

Three call sites then hard-code the rationale "Evidence thresholds met, FTO recommendation accepted" — a factual assertion the code never checked, written into the immutable record under a named decider.

The sharpest case: a row queued as SIGNED OFF - REVIEW REQUIRED means the trainee performed the skill unsafely after being signed off. approveAllReadyV20_1 picks it up like any other row. On the next rebuild the new decision post-dates the unsafe event, so the flag clears and readiness reverts to plain SIGNED OFF. One menu click erases a post-sign-off safety flag and replaces it with a competency attestation.

The paramedic dual sign-off gate has four silent bypasses

needsDualSignoffV19_ returns false — falling through to the single-signature path that closes the queue item — on any of: the trainee failing an exact-string lookup in a 40-row window, a level string that isn't exactly Paramedic or Advanced EMT, a phase that isn't exactly Phase 4, or a release filed under any other item type.

Safety alerting

Every path below can stop an urgent notification from reaching a human, without producing an error anywhere.

High
Code.gs:389Code.gs:3549

One mail failure kills every later alert in the same submission

sendMail rethrows on failure, and evalAlerts is a bare sequence of six sends with no try/catch around any of them — with each queueAdd running after its send. A quota exhaustion on the first send means the controlled-substance alert, the red-flag alert, the Medical Director notice, the NRT alert and the advancement alert all never happen — and their 72-hour queue rows are never created, so the breach detector has nothing to find.

High
Code.gs:1486Code.gs:1515

The retry guard overwrites itself

alreadyMirrored is true only when the ledger state is exactly VALIDATED — but the catch writes FAILED, overwriting it. Any post-mirror failure therefore guarantees a second mirror write on retry, and the alerts sit outside the guard entirely, so they re-fire too.

The inverse is worse: if the platform does not retry, the evaluation sits on tab 02 with no unsafe-score alert ever sent. The comment asserting "Apps Script retries" is not reliable for installable triggers.

High
Code.gs:4632Code.gs:3554Code.gs:1421

A form-question reorder silently corrupts every eval alert

The eval path reads entirely by fixed position — EV.CS, EV.REDFLAG, v[12 + i] for the six domain scores — and there is no header verification on this path anywhere in the file. classifySheetEventV20_1_ inspects exactly one cell.

Insert a question anywhere in positions 3–12 and the row still classifies as an eval, but every index shifts. Real unsafe scores produce nothing, and unrelated "Yes" answers produce false urgent alerts and phantom 72-hour clocks. Move or rename the "FTO name" question instead and the submission is quarantined with nothing mirrored and no alert of any kind.

The inconsistency proves the fix is known: the skills handler reads the same form by header name. Only the safety-critical reader is positional.

Platform limits

Apps Script gives you six minutes per execution and, on a consumer account, 100 mail recipients per day. Both are already at risk.

High
Code.gs:4237Code.gs:4350

The matrix rebuild is a full workbook re-render on every write

rebuildSkillMatrixV19_ does not just write data. It also calls rewriteEngineSkillMetricV19_ (40 individual formula round trips), refreshSkillValidationQueueV19_ → runSkillAuditV20 (one setValue per open queue row), and applySkillsLayoutV19_ — which repaints roughly a quarter-million cell formats, rebuilds nine conditional-format rules, and recreates filters on four sheets.

It runs on every skill submission, every recorded decision, every trainee close, and every new name typed on tab 01. A timeout inside the submit lock leaves the ledger stuck at RECEIVED, because a hard kill never reaches the catch.

This is the single highest-leverage change available. Splitting the data write from the presentation repaint, and batching the three per-cell loops, takes the per-submission cost from tens of seconds to under one — and removes the row-shift corruption as a side effect, since a single post-loop rebuild sorts once, after all writes are done.

All ten locked functions and every caller were traced. Nothing nests, so the deliberate throw never fires in practice. The finally block resets the flag before releasing, and Apps Script re-initialises globals per execution, so staleness is impossible.

The caveat: the batch paths avoid nesting by running unlocked, which is where the row-shift corruption lives.

Suggested order of work

Sized for one part-time maintainer. Every step is independently shippable and nothing here requires a rewrite.

  1. Get a safety net before touching logic. clasp clone, commit the current build as a baseline, push it. Then add a Tests.gs that runs inside Apps Script — no npm, no mocks — with a dozen assertions against the pure functions.

    2–3 hours · makes every later change reviewable and reversible

  2. Restore the skills pipeline. catalogEntry.approval → .status; fix the prompting vocabulary; move the unsafe-outcome alert outside the acceptance gate.

    under an hour · three edits, and the system starts doing its job again

  3. Stop the record-destroying tools. Run unwrapAuditFormulasV20_1. Delete simplifyFlagsV20_1 and the narrative-rewriting block of fixAllFlagsNowV20_1. Begin reconciling tab 02 against the Form response history.

    half a day, plus reconciliation time

  4. Fix the two corruption paths. Re-derive queue rows by REQUEST ID inside each loop iteration rather than trusting the pre-loop snapshot, and make the CANCELLED : CRITERIA CHANGED sweep skip rows that carry a decision.

    2 hours

  5. Gate the mutating menu items. The authorization model already exists and is sound — call it from advancement, close/release, bulk approval, mode switching, the scoreboard and the backup. Then delete the name-matching fallback so an unidentifiable session refuses rather than guesses.

    2–3 hours · highest security value per line changed

  6. Make alerting survive failure. Wrap each send in evalAlerts and dailyChecks in its own try/catch; create the queue row before attempting the mail; header-map the eval path; surface ledger QUARANTINED counts and the effective mail mode in systemHeartbeat.

    a day

  7. Split data from presentation in the rebuild. Drop the layout and engine-formula calls out of rebuildSkillMatrixV19_, batch the three per-cell loops into single setValues calls, and call the rebuild once per batch instead of once per row.

    half a day · removes the timeout risk and most of the latency

  8. Delete what is provably dead. 36 zero-reference functions (~984 lines), 10 never-read constants, and the three stale inventory lists whose entries are 73% fictional. Commit each category separately.

    1–2 hours · the file drops ~10% and stops offering three competing answers to the same problem

Before you act on this

Four things to check against your live sheet, not the source
  • Queue column alignment. setupQueueReviewV20 is called from nowhere and is on no menu, so on a fresh install REQUEST ID and RECORD land in columns 14 and 15 — while the code hard-codes 14 for REVIEW and 16 for RECORD. That would mean the audit overwrites request IDs and the RECORD checkbox does nothing. But the function's own message says "Run once," so it may well have been run manually from the editor. Check tab 20's actual header row.
  • Trigger identity. Whether Session.getActiveUser().getEmail() inside the installable onEdit trigger returns the editor or the trigger owner. If it returns the owner, every checkbox sign-off is stamped verified under one identity regardless of who ticked it. Cheap to test with a second account, high consequence either way.
  • The portal file. portal.html was not part of what I reviewed. If it contains anything beyond static cards and form links, it is world-readable through the deployed web app.
  • Manually created triggers. The dead-function list assumes the 8 managed handlers are the only roots. A trigger added by hand in the Apps Script UI would not appear in the source — check the project's trigger list before deleting anything you don't recognise.
How these findings were produced

Six independent review passes over the same file, each with a different brief: correctness, security and privacy, concurrency and data integrity, platform limits, architecture, and domain risk. Each was asked to verify every claim against actual lines and to mark anything uncertain.

I then re-checked the load-bearing claims myself at the source — the approval property, the prompting mismatch, the identity flag, the sort-during-loop, the cancel sweep, the authorization call sites, the row windows, the missing trigger, and the escaping gaps. Everything presented above as fact was confirmed that way. Where a reviewer could not verify something, it is in the checklist above rather than in the findings.

Two reviews independently found the approval bug from different directions, which is the strongest signal in the set.
