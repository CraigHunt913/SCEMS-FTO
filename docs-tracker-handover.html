Tracker Handover

Getting a clean tracker without losing the forms, the responses, the thirteen thousand lines of script, or a single record. About an hour, and reversible until step 11.

Read this before anything else

The Apps Script lives inside the spreadsheet. Deleting the spreadsheet deletes all 13,726 lines of it and every trigger with it. Your nine forms survive — their responses are stored in the forms, not in the sheet — but the machinery that turns a submission into a record does not.

So nothing gets deleted. We copy, clean the copy, move the forms across one at a time, and leave the original sitting there working until the new one has proved itself.

1

Before you touch anything

Nothing at risk

Two minutes, and it is the difference between a bad afternoon and a disaster.

  1. Save the backup

    The zip I sent has all 52 tabs and 4,604 rows as CSV. Put it somewhere that is not Google Drive. If everything below goes wrong, that file is the floor you land on.

  2. Take Google's own backup too

    In the tracker's script editor, run this. It writes a dated copy into your backup folder, and it is a native Google copy, so it keeps things a CSV cannot.

    fullBackupV20_1()

  3. Write down the old spreadsheet's id

    It is the long string in the address bar between /d/ and /edit. You will need it at the end to be certain you are retiring the right file.

2

Make the copy and clean it

Nothing at risk

The copy is a new file. Everything you do to it is invisible to the tracker everyone is still using.

  1. File → Make a copy

    Name it something you will recognise — SCEMS Field Training Tracker v21 will do. Google copies the Apps Script with it, which is why this method works at all.

    What you should seeA new spreadsheet with all 52 tabs and, under Extensions → Apps Script, the whole script already there.
    What does not come acrossTriggers. The copy has the code but nothing is scheduled and no form is bound. That is fixed in phase 4, and until then the copy is inert, which is exactly what you want while you work on it.

  2. Paste the new script into the copy

    In the copy: Extensions → Apps Script → select all → delete → paste the Code.gs I sent → Save. Do this in the copy only.

  3. See what would come out

    freshStartReport()

    Read it. It lists every removable tab with its row count and changes nothing. It will only ever offer you two kinds: a Form Responses N that no form is writing to, and a tab ending LEGACY V18.

    What you should seeAround seventeen tabs offered, and the tabs a form is writing to listed separately as kept. Nothing the code names is ever on the removal list.

  4. Take them out

    The token includes the spreadsheet's own name, so a command pasted from somewhere else cannot run against the wrong file. Copy it from the end of the report.

    freshStartClean("CLEAN your copy's name")

  5. Fix what is actually broken

    In this order. Each one reports before it writes.

    engineHealthCheck()
previewEngineRepairV20_6()
applyEngineRepairV20_6("REPAIR THE ENGINE KEY COLUMN")
repairDecisionQueueHeaderV20_4()
protectRecordTabsV20_2()
    What you should seeThe engine check finds one #REF! and one crossed cell, then finds nothing on the second run. Give the sheet a few seconds to recalculate between the repair and the re-check.
    Two rows it will not fixTwo rows on the trainee master hold a clearance and no name. Only you know who they are. Putting a name on a personnel record is not something a tool should decide, so it reports them and stops.

  6. Look at it

    Open every tab. The dashboard and the views should have no #REF! anywhere. This is the moment to decide you like it, because the next phase is the one that commits.

The point of no return is the next step

Everything so far can be undone by closing the copy and walking away. Relinking the first form cannot: a form has exactly one destination, so pointing it at the copy points it away from the original. The original stops receiving new submissions from that form.

Before you go on:

  • The backup is saved somewhere outside Drive.
  • The copy has no #REF! left in it.
  • Nobody is mid-shift about to submit an evaluation. Early morning is the right time.

Old responses are not at risk either way — Google copies every existing response into the new destination when you relink. It is only the next submission that follows the form.

3

Move the nine forms

Commits, one form at a time

One at a time, verifying each before starting the next. If something looks wrong on form one, you have eight still pointing at the old tracker and a working system to go back to.

  1. For each form, in turn

    Open the form → Responses → the sheets icon → Select existing spreadsheet → choose the copy.

    What you should seeA new tab appears in the copy holding every response that form has ever had. Check the row count against the same form's tab in the old tracker before moving on.

  2. Do not stop halfway

    The window that drops submissionsBetween relinking a form and installing its trigger in phase 4, a submission to that form lands in the sheet but nothing turns it into a record. onHubFormSubmit refuses it, because that form is meant to be handled by its own bound trigger.

    Do all nine and then phase 4 in one sitting. If you must stop, stop before you start, not between forms.

4

Wake the copy up

Verify each

The copy has all the code and none of the wiring. This puts the wiring back.

  1. Find the forms, then rebuild every trigger

    rebuildFormIdsNow()
repairAllTriggersNow()

    The first rescans Drive for the nine forms and prefers the ones now linked to this spreadsheet. The second removes every stale trigger and installs eight scheduled ones plus the form-bound ones.

    What you should see9 of 9 form-bound. Anything less names the forms it could not find, and a form with no bound trigger drops its submissions — do not leave it at eight.

  2. Prove it end to end

    Submit one real evaluation through a form. Watch it appear in 02 FTO SHIFT EVAL RAW and in 91 INGESTION LEDGER. That single test exercises the form, the trigger, the handler, the mirror and the ledger in one go.

  3. Catch anything that arrived in the gap

    catchUpUnprocessedPreview()
catchUpUnprocessed()

    Replays any response that landed while nothing was listening. Safe to run twice — the ledger stops it doubling.

5

Point the portal at it

Verify each

The portal is a separate script project, so it survives all of this untouched. It just needs to be told where to look.

  1. Give it the new id

    In the portal project: Project Settings → Script Properties → PORTAL_PRODUCTION_SPREADSHEET_ID → paste the copy's id. Then, in order:

    pointAtProductionReadOnly()
productionReadinessCheck()
goLive()
    What you should seeThe readiness check naming the new spreadsheet, and every tab found. Read it before running goLive().

  2. Deploy

    Deploy → Manage deployments → edit → New version. Your QR code and the /exec address do not change.

6

Retire the old one — not yet

Reversible

The temptation is to delete it today. Don't.

  1. Run the full review on the new one

    fullSystemReviewV20_1()
tabNameCheck()
engineHealthCheck()

    All three read-only. Do not retire anything until these come back clean.

  2. Rename the old one so nobody opens it by accident

    ZZ OLD TRACKER — DO NOT USE — replaced 23 Aug 2026. Check the id against the one you wrote down in phase 1 before you rename it.

  3. Leave it alone for thirty days

    It costs nothing to keep and it is the only thing that can answer a question the new one gets wrong. After a month of the new tracker working, delete it or don't — by then it does not matter.

Nothing in this procedure deletes anything from the original tracker.
Every command listed reports before it writes, and the ones that write are gated twice:
a token that names what it is about to do, and an authorisation check on top of it.
